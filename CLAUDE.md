# duongondro-android

Kotlin + Jetpack Compose + Material 3 app for Duongöndro, minSdk 28. The design lives in `Duongondro/duongondro-design` (read its `README.md` and `CLAUDE.md` first, then `docs/16-implementation-plan.md`); phase 6 is tracked in duongondro-design#6.

- **Build and test locally on the Mac, not on GitHub CI.** `make core-test`, then `make build`; `make install` puts the debug APK on the running emulator. Use the one emulator already set up (`Medium_Phone`); never create more AVDs or download system images.
- **The Makefile uses Android Studio's bundled JDK** (`~/Applications/Android Studio.app`); the Gradle wrapper pins Gradle, `gradle/libs.versions.toml` pins everything else.
- **Logic lives in `core/`**, a pure Kotlin JVM module tested with `./gradlew :core:test`, mirroring `DuongondroCore` on iOS. `core/src/test/resources/streak-cases.json` (and later `vectors.json`) are copies of `duongondro-api/testdata/`; refresh them from there, never edit them here.
- **Day keys** are `java.time.LocalDate` built from an instant in an explicit `ZoneId` (`civilDate`), never a formatter with `YYYY`.
- **Theme tokens only** (`ui/theme/`): colours and the small shape scale (4 dp small components, 6 dp buttons, cards and the FAB), no literals in composables. Light and dark designed together.
- **Never log from Today.** Counts are logged only on a practice's screen, through `PendingLog` (5-second undo window; the session is written at once, pending, counted on screen but never synced until the window closes; Undo deletes it; no source recorded).
- **Release builds refuse a dirty tree**; debug builds show `<hash>-dirty` in Settings.
- **Practice names:** Tibetan/Sanskrit first (Dorje Sempa, Chenrezig, Amitabha), English as the second line.
- Commits end with the attribution trailers the session asks for.
- **Sign-up order** (`ui/onboarding/AccountScreens.kt`, as on iOS): consent (GDPR Art. 9; nothing is created before it) → passkey, which makes the account with no profile ("Use email instead" makes it by magic link) → display name (the server's name for the new account filled in; Skip keeps it, an empty one shows as "A friend") → gender (Skip) → e-mail (Skip; a second way to sign in, confirmed by a mailed code; skipped for an account made by e-mail) → recovery code. Keys are made silently as soon as the account exists; a relaunch before the recovery code is confirmed resumes at the name while the session lives. No e-mail, username or name is ever required; the username is not asked for at all. A friendship link opened before sign-up is checked when the passkey or e-mail is sent and goes with the sign-up as proof; the friendship follows once keys exist. Otherwise friendship codes are entered from Friends after sign-up. Sign-in is passkey or emailed link and needs no identifier for a passkey.
- **Accounts against the local server:** debug builds talk to `http://10.0.2.2:8080` (`make serve` in duongondro-api; magic-link codes are printed to its log; another URL with `-Pduongondro.apiUrl=…`). Passkeys cannot be exercised there: the DEV server's relying party is `localhost`, and Credential Manager needs `duongondro.app` with its assetlinks.json and the APK's `android:apk-key-hash:` origin in the server's `RP_ORIGINS`. Sign up with "Use email instead" on the emulator; try passkeys on a phone against production. `DUONGONDRO_API_URL=http://127.0.0.1:8080 make core-test` also runs `LiveServerTest` against it.
- **Release signing:** `make apk` builds the sideloadable release APK. The key never enters the repository: `~/.config/duongondro/android-release.properties` (or `-Pduongondro.signing=<file>`) names `storeFile` and `keyAlias`, and the passwords come from `DUONGONDRO_STORE_PASSWORD` / `DUONGONDRO_KEY_PASSWORD`. Without them the APK is unsigned. Its certificate's SHA-256 is what production's `ANDROID_CERT_SHA256` and the `android:apk-key-hash:` passkey origin are made from; losing the key means no updates for anyone who installed the app.
- **Firebase** (project `duongondro-43f6c`, push only, no Analytics): `app/google-services.json` is committed on purpose. Its values ship in every APK anyway; the Android API key is restricted in Google Cloud to `app.duongondro` signed with the release key (SHA-1 `37:9E:CC:0E:F9:A6:A0:9F:52:9D:CD:5B:08:D8:5F:95:0D:A3:AC:EF`) or the owner's Mac's debug key (SHA-1 `A7:F2:F6:70:EF:3C:7A:28:CA:5B:AB:C7:7B:04:20:B0:32:28:8E:25`), and to the Firebase Installations, FCM Registration and Firebase Cloud Messaging APIs. A debug build from another machine gets no push token until its debug SHA-1 is added there. The server sends with the service account in the vault, never with this key.
- **Push** (design: Social › Nudges, Localisation): the server sends FCM notification messages with `body_loc_key`/`body_loc_args` and the sender's thread as `tag`; `PushKey` in `core/.../Push.kt` lists the keys (`PushTest` checks them against `duongondro-api/internal/service/nudges.go` when a checkout is beside this one), and each is a string of that exact name in `res/values*/strings_push.xml` in all nine languages (`PushStringsTest`). **0.4 is always discreet** (the owner's decision): the system draws those strings itself in the background, so FRIEND_DONE* and POKE* use only the name (`%1$s`) and STREAK_AT_RISK no argument, never a practice or a day count; in the foreground `PushService` draws the same text. 0.5 moves to data-only messages rendered by the app (practice names, plurals, the Discreet setting). Firebase initialises locally at launch; no network call and no Installation ID until an account with keys and notifications allowed: auto-init and notification delegation are off in the manifest, and `Push.refresh` turns auto-init on and sends the token (as `fcm`, resent when it, the device id or a day changes). Signing out, switching account, deleting everything and a session the server ended delete the token and then the Firebase Installation, retried at each launch and return to the foreground until it succeeds, and turn auto-init off. The permission is asked on Friends (a card; "Not now" is remembered), on "Tell me when they practise" and after a poke, never at launch. A 0.4 limit: tapping a push only opens the app (iOS opens the friend's page). A token needs a Google Play emulator image and this Mac's debug SHA-1 on the API key (see Firebase above).
- **Releases:** bump `versionCode` (by one) and `versionName` in `app/build.gradle.kts` in a commit of their own, push, then `make publish NOTES=<file>`: it refuses a version already released, a `versionCode` not above the last release's, and an unpushed HEAD. The landing page's download link always serves the newest release's `duongondro.apk`.
